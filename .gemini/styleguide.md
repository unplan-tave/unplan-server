# Code Review Style Guide

## Language

* 모든 리뷰 코멘트, 요약, 제안은 반드시 한국어(ko-KR)로 작성한다.
* 코드 식별자, 에러 메시지, 라이브러리 이름은 원문을 유지한다.
* 설명은 간결하고 실행 가능한 형태로 작성한다.

## Review Priority

다음 항목을 우선적으로 리뷰한다.

1. 버그 가능성
2. 보안 취약점
3. 인증/인가 누락
4. 예외 처리 누락
5. 트랜잭션 처리 문제
6. API 응답 형식 불일치
7. DB 쿼리 성능 문제
8. 중복 코드 또는 과도한 책임 분리 실패
9. 테스트 누락

## Backend Review Rules

* Controller는 요청/응답 처리에 집중하고, 비즈니스 로직은 Service에서 처리해야 한다.
* Service는 핵심 비즈니스 로직을 담당하고, Repository 접근은 필요한 범위로 제한한다.
* DTO와 Entity를 명확히 분리한다.
* Entity를 API 응답으로 직접 반환하지 않는다.
* 사용자 입력값은 반드시 검증한다.
* 인증이 필요한 API는 인증/인가 처리가 누락되지 않았는지 확인한다.
* 예외는 공통 예외 처리 방식에 맞게 처리한다.
* 민감한 정보는 로그, 응답, 에러 메시지에 노출하지 않는다.
* DB 변경이 있는 경우 마이그레이션 필요 여부를 확인한다.
* N+1 쿼리, 불필요한 전체 조회, 반복문 내부 DB 호출을 지적한다.

## Comment Style

* 문제 원인을 먼저 설명한다.
* 수정 방향을 구체적으로 제안한다.
* 가능하면 간단한 코드 예시를 포함한다.
* 확신이 낮은 내용은 코멘트하지 않는다.
* 단순 취향 차이인 경우 코멘트를 남기지 않는다.
* 이미 lint, formatter가 처리할 수 있는 내용은 지적하지 않는다.
* 중요도가 낮은 사소한 표현 개선은 최소화한다.

## Comment Format

리뷰 코멘트는 아래 형식을 따른다.

**문제:**
무엇이 문제인지 설명한다.

**이유:**
왜 문제가 되는지 설명한다.

**제안:**
어떻게 수정하면 좋은지 제안한다.

## Do Not Comment

* 단순 코드 스타일 취향
* formatter로 자동 수정 가능한 내용
* 동작에 영향 없는 사소한 변수명 취향
* PR 범위와 직접 관련 없는 대규모 리팩토링 제안
* 근거 없는 추측성 지적
